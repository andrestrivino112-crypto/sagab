1. Visión general y arquitectura

SAGAB es una aplicación web de tres capas. El navegador ejecuta una SPA React; esta consume una API REST Spring Boot mediante JSON o multipart/form-data; la API persiste información en PostgreSQL y archivos en un directorio persistente o proveedor compatible con S3.

Usuario / navegador │ HTTPS ▼ Frontend React + TypeScript (SPA estática) │ REST JSON / multipart + Bearer JWT ▼ Backend Spring Boot 3 · Tomcat embebido ┌────┴───────────┬────────────────┐ ▼ ▼ ▼ PostgreSQL Storage local/S3 SMTP opcional sagab + adjuntos avisos financieros auditoria

1.1 Responsabilidad de cada capa

CapaResponsabilidadesNo debe asumir
FrontendPresentación, navegación, captura, validación inmediata, estado de sesión, descargas y experiencia por rol.No es una frontera de seguridad. Ocultar un botón no autoriza ni protege un dato.
BackendAutenticación, autorización, validación definitiva, reglas de negocio, archivos, reportes, auditoría y transacciones.No debe confiar en IDs, roles, tipos MIME o valores calculados enviados por el cliente.
PostgreSQLIntegridad referencial, restricciones, índices, auditoría, estados y persistencia transaccional.No reemplaza las comprobaciones de propiedad contextual realizadas en servicios.
InfraestructuraHTTPS, DNS, disponibilidad, secretos, red, copias, almacenamiento, métricas y alertas.No forma parte automáticamente del código de aplicación.

1.2 Flujo normal de una petición

  1. El usuario inicia sesión mediante POST /api/auth/login.
  2. El servidor verifica usuario, estado, bloqueo y hash BCrypt; devuelve JWT y datos mínimos de sesión.
  3. El frontend guarda el JWT en sessionStorage y adjunta Authorization: Bearer ….
  4. El filtro JWT valida firma/expiración y construye la identidad de Spring Security.
  5. Las reglas HTTP, @PreAuthorize y el servicio validan rol y alcance.
  6. Repositorio/JPA ejecuta la transacción; restricciones y triggers completan la integridad/auditoría.
  7. La API devuelve DTO JSON, descarga binaria o error normalizado sin traza interna.

3.1 Convenciones

  • El código backend usa el paquete raíz ec.edu.bellini.sagab.
  • Los endpoints de aplicación empiezan con /api.
  • La interfaz utiliza importación diferida de vistas para separar chunks.
  • Los cambios estructurales de datos deben agregarse como scripts idempotentes y probarse en una base limpia.
  • Los datos demo o personales nunca deben ejecutarse automáticamente en producción.

4. Arquitectura del backend

4.1 Capas

CapaFunciónRegla de mantenimiento

DTODefine contratos y validaciones de entrada/salida.No exponer entidades JPA directamente.

4.2 Manejo de errores

Los errores de negocio y validación se convierten a respuestas HTTP mediante el paquete exception. El servidor tiene server.error.include-stacktrace=never, por lo que una respuesta no debe revelar SQL, rutas, clases ni secretos. El frontend busca el campo mensaje; si no existe, presenta el estado HTTP.

EstadoInterpretación operativa
400Solicitud inválida, dato fuera de rango o regla de negocio incumplida.
401Token ausente, inválido o expirado. El cliente limpia la sesión activa.
403Rol o propiedad insuficiente.
404Recurso inexistente o no visible para esa identidad.
409Conflicto o duplicado lógico.
413Archivo o petición demasiado grande, según infraestructura/configuración.
500Error no controlado; correlacionar hora y usuario con logs sin entregar detalles internos al cliente.

4.3 Procesos programados

ProcesoProgramaciónAcción
Obligaciones vencidasAl arrancar y cada día a las 02:00.Cambia obligaciones pendientes cuya fecha venció a VENCIDO.
Partición de auditoríaAl arrancar y el día 1 de cada mes a las 03:00.Crea preventivamente la partición mensual necesaria.

La zona horaria JDBC está configurada como America/Guayaquil. Debe alinearse con la zona del contenedor y de PostgreSQL para evitar cortes de fecha inconsistentes.

5. Arquitectura del frontend

5.1 Arranque y sesión

App.tsx recupera la sesión con /api/auth/me, fuerza la pantalla de cambio de clave cuando corresponde y elige la ruta inicial según el primer rol recibido. El token se guarda en sessionStorage bajo sagab_token; por tanto no se comparte entre sesiones de navegador y se elimina al cerrar sesión o recibir 401.

Decisión actual. No se utiliza refresh token en el flujo activo, aunque existe una tabla de base para ello. Al vencer el JWT de 30 minutos, la persona debe autenticarse otra vez.

Las rutas usan guardas visuales y redirección, pero la autorización real debe mantenerse en el backend. Representante y Estudiante utilizan un layout propio; no usan el Sidebar institucional.

5.3 Cliente HTTP

  • api(): JSON, agrega Bearer y normaliza errores.
  • apiForm(): FormData; no fija manualmente Content-Type para conservar el boundary.
  • apiBlob(): reportes/descargas autenticadas.
  • Un 401 con token previo dispara sagab:sesion-expirada.
  • La URL base proviene de VITE_API_URL, con fallback http://localhost:8080.

5.4 Compilación

Las vistas son chunks diferidos. Vite desactiva mapas de fuente de producción y separa algunas dependencias pesadas. Se sustituyó el CSS Bootstrap completo de aproximadamente 280 KB por forms-scoped.css y las fuentes Inter se limitaron a Latin; el directorio de producción bajó aproximadamente de 3,2 MB a 2,2 MB. El chunk de gráficos sigue cerca de 553 KB antes de gzip, pero solo se solicita al abrir el panel.

Medición Lighthouse. No evaluar npm run dev con extensiones del navegador activas. La captura de referencia con puntuación 45 indicaba interferencia de extensiones. La medición válida debe hacerse contra el build de producción, en incógnito o en un perfil limpio, y repetirse varias veces.

  • Calificación única por estudiante/asignación/parcial.
  • Índices parciales aceleran usuarios no activos, estudiantes activos, notas en riesgo, ausencias injustificadas, mora y pagos en revisión.

6.3 Instalación del esquema

database/setup_db.sh crea la base local si hace falta y aplica 23 scripts estructurales. El orden no es el orden numérico literal: 09_estudiante_usuario.sql debe ejecutarse antes de 07_usuario_username.sql; el script ya contiene el orden verificado.

No ejecutar datos demo en producción. Los scripts 05, 08, 11 y 24 son datos/cuentas de prueba. Los scripts 07 y 10 contienen cuentas personales y deben revisarse, sanearse o sustituirse por un aprovisionamiento controlado.

El proyecto no utiliza Flyway ni Liquibase. La versión instalada debe registrarse externamente y cada cambio debe probarse contra una copia y una base vacía.

7. Seguridad y autorización

7.1 Autenticación

  • API stateless, sin sesión HTTP de servidor.
  • Contraseñas con BCrypt, factor de costo 12.
  • JWT HMAC-SHA256 con duración de 30 minutos.
  • Bloqueo después de 5 intentos fallidos durante 15 minutos.
  • Cambio obligatorio de la clave temporal.
  • Registro de acceso exitoso/fallido en eventos de seguridad.

SecretsGuard impide arrancar si no existen las variables SAGAB_DB_PASSWORD y SAGAB_JWT_SECRET, evitando usar silenciosamente los valores de ejemplo.

7.2 Superficie pública

RecursoMotivoControl compensatorio
POST /api/auth/loginEntrada al sistema.Validación, bloqueo y auditoría.
GET /api/storage/local/{token}Permite abrir/mostrar un archivo sin poder adjuntar Bearer desde ciertos contextos.Token HMAC firmado, corto y emitido solo tras autorizar el recurso.

Todo otro endpoint requiere autenticación.

7.3 Autorización por capas

Rol de aplicaciónAlcanceRestricción principal
ADMINAdministración y operación institucional.Acceso a matrícula, académico, asistencia, calendario, mensajes, finanzas y personal.
DOCENTEGestión académica de sus asignaciones.Limitado a sus materias y paralelos.
DECESeguimiento y alertas estudiantiles.Acceso especializado a información de acompañamiento.
AUDITORConsulta de trazabilidad y panel.Sin operación académica.
REPRESENTANTEConsulta de representados.Limitado a estudiantes vinculados.
ESTUDIANTEConsulta y participación propia.Limitado a su identidad estudiantil.
  1. SecurityConfig: reglas generales por ruta/método.
  2. @PreAuthorize: roles permitidos en controlador.
  3. Servicio: propiedad y alcance: docente asignado, estudiante propio, representado vinculado, remitente autorizado.
  4. Base: claves foráneas, unicidad, checks y triggers de integridad.
Alcance corregido. Docente ya no recibe promedio, rendimiento ni mora institucional; sus ausencias se limitan a paralelos activos asignados. /dashboard/promedio y /finanzas/mora quedan reservados a Administración y Auditoría según el endpoint.

7.4 Cabeceras, CORS y CSRF

  • CORS acepta solo orígenes exactos de SAGAB_CORS, métodos GET/POST/PUT/PATCH/DELETE/OPTIONS y cabeceras Authorization/Content-Type.
  • X-Frame-Options: DENY reduce clickjacking.
  • X-Content-Type-Options está habilitado.
  • HSTS se emite para un año e incluye subdominios; solo tiene efecto real sobre HTTPS.
  • CSRF se desactiva porque la API usa Bearer y no cookie de autenticación.

7.5 Recomendaciones para producción

  • HTTPS obligatorio, TLS moderno y redirección HTTP→HTTPS en proxy/plataforma.
  • Secretos en un gestor, rotación, acceso mínimo y nunca en Git/logs.
  • Base y bucket privados; firewall y credenciales distintas por entorno.
  • Agregar Content-Security-Policy, Referrer-Policy y Permissions-Policy tras pruebas.
  • Protección de tasa para login y endpoints costosos, además del bloqueo por cuenta.
  • Antivirus/escaneo asíncrono de archivos si se aceptan documentos reales.
  • Prueba OWASP, revisión de dependencias y modelo de amenazas antes del contrato.

10. Almacenamiento y archivos

10.1 Selección de proveedor

Si están presentes todas las variables esenciales S3 —endpoint, bucket, access key y secret key— se usa el proveedor compatible. Si todas faltan, se usa almacenamiento local. Una configuración parcial debe rechazarse para evitar escribir archivos en un destino inesperado.

ModoUsoRiesgo/condición
LocalDesarrollo o servidor con volumen persistente.Un filesystem efímero pierde adjuntos al desplegar; requiere volumen y respaldo.
S3 compatibleProducción distribuida: AWS S3, R2 u otro compatible.Bucket privado, CORS del bucket, política mínima, cifrado y lifecycle.

10.2 Controles

  • Claves/nombres internos aleatorios y defensa contra recorrido de rutas.
  • Comprobación de extensión, MIME declarado y firmas/magic bytes.
  • Autorización antes de emitir descarga.
  • En modo local, URL HMAC firmada con caducidad aproximada de 10 minutos.
  • Hash SHA-256 del comprobante financiero para detectar duplicado en una obligación.

10.3 Límites

TipoLímite lógicoConfiguración
Entrega/deber y calendario15 MB por archivoSAGAB_UPLOAD_MAX_MB_DEBERES
Comprobante8 MBSAGAB_UPLOAD_MAX_MB_COMPROBANTE
Recurso académico100 MBSAGAB_UPLOAD_MAX_MB_RECURSOS
Multipart global100 MB por archivo/petición por defectoSAGAB_UPLOAD_MAX_MB
Adjuntos de evento10 archivosRegla de servicio

El límite global debe ser igual o mayor al máximo lógico. El proxy/CDN también debe aceptar el tamaño necesario; si su límite es menor, responderá antes que Spring.

12.1 Prerrequisitos

El script supone que el usuario del sistema puede listar y crear bases con las credenciales locales configuradas en PostgreSQL. En un servidor administrado, aplique los scripts con una cuenta de migración y no con la cuenta runtime.

Verifique el arranque en el log y que no aparezcan fallos de validación Hibernate. No copie el secreto generado a documentación, tickets o Git.

Abra http://localhost:5173. Para exponer temporalmente en la red local, use npm run dev -- --host 0.0.0.0, ajuste CORS al origen exacto y permita el puerto en firewall. No es una configuración de producción.

  1. Crear base, roles y secretos rotados.
  2. Respaldar antes de cada cambio.

La plantilla actual aprovisiona PostgreSQL y backend en plan gratuito, pero no incluye el frontend y mantiene un placeholder en SAGAB_CORS. 14. Operación, respaldo y recuperación

14.1 Responsabilidades diarias

FrecuenciaControl
ContinuoDisponibilidad HTTP, errores 5xx, latencia, uso de conexiones, almacenamiento y fallos de login anómalos.
DiarioEstado de backup, jobs de vencimiento, capacidad, errores de storage/SMTP y cola financiera.
SemanalRevisión de seguridad, cuentas activas, crecimiento de auditoría y restauración de muestra.
MensualPartición de auditoría, parches, dependencias, capacidad y revisión de accesos.
Por periodoCatálogos, asignaciones, políticas de notas, archivo y retención.

14.2 Política mínima de respaldo

  • PostgreSQL: backup diario automático y copias incrementales/PITR si el proveedor lo permite.
  • Archivos: versionado o réplica del bucket/volumen.
  • Secretos/configuración: inventario cifrado y recuperable por dos responsables.
  • Copias fuera del mismo proveedor o zona de fallo.
  • Retención definida por calendario académico, normativa y contrato.
  • Prueba de restauración completa al menos trimestral y antes de cambios mayores.

Ejemplo conceptual; sustituir host, rol y ruta mediante variables seguras y no colocar la contraseña en la línea de comandos:

pg_dump -Fc --no-owner --no-acl -h DB_HOST -U BACKUP_ROLE sagab \
  -f /backup/sagab_YYYYMMDD.dump

createdb sagab_restore_test
pg_restore --clean --if-exists --no-owner -d sagab_restore_test \
  /backup/sagab_YYYYMMDD.dump

14.3 Objetivos de recuperación

Rectorado y proveedor deben acordar formalmente RPO (pérdida máxima de datos aceptable) y RTO (tiempo máximo de recuperación). Valores orientativos como RPO 24 h/RTO 8 h no son una garantía del código; dependen del plan contratado y deben probarse.

14.4 Procedimiento de incidente

  1. Registrar hora, síntoma, alcance, despliegue reciente y quién reporta.
  2. Proteger evidencia y limitar accesos; no modificar auditoría.
  3. Clasificar disponibilidad, confidencialidad, integridad o operación.
  4. Contener: revocar secretos/sesiones, aislar servicio o desactivar función según riesgo.
  5. Recuperar desde versión/backup verificado y validar procesos críticos.
  6. Notificar según contrato y normativa; documentar causa y acciones preventivas.

18. Riesgos, deuda técnica y hoja de ruta

18.1 Bloqueantes antes de producción comercial

  1. Validar integralmente autorización y privacidad. La matriz y el alcance del panel fueron corregidos; falta probar acceso negativo de todos los endpoints y roles en integración/E2E.
  2. Crear pruebas de integración y E2E. Cubrir flujos críticos y cada endpoint por rol/ownership.
  3. Automatizar CI/CD seguro. Pruebas, type-check, build, escaneo, imagen, migración y smoke test.
  4. Definir backup/restore y almacenamiento persistente. Ejecutar una restauración comprobable de DB y adjuntos.
  5. Desplegar HTTPS con monitoreo. Métricas, alertas, logs, incidentes y SLA contratados.
  6. Gestión administrativa de cuentas. Desactivar, editar, restablecer y revocar sesiones con auditoría.
  7. Evaluación de privacidad y seguridad. Datos de menores, financieros y DECE exigen mínimo privilegio, retención y respuesta a incidentes.

18.2 Prioridad alta

  • Migrar scripts a Flyway/Liquibase y eliminar credenciales/cuentas personales de scripts de distribución.
  • Implementar cierre de parciales, autorización de correcciones y trazabilidad académica amigable.
  • Completar matrícula: lista, edición, retiro/promoción/rematrícula y expedientes.
  • Completar asistencia: atraso, justificativo, evidencia y aprobación.
  • Crear catálogos administrativos de periodo, materia, paralelo y rubro.
  • Documentar API mediante OpenAPI y añadir versionado.
  • Mejorar auditoría visual, filtros y exportación autorizada.

18.3 Evolución funcional

  • Facturación electrónica e integración contable solo después de análisis regulatorio.
  • Planificación, horarios, rúbricas y actas académicas.
  • Flujos especializados de DECE con compartimentación y consentimiento.
  • Eventos recurrentes e integración con calendarios externos.
